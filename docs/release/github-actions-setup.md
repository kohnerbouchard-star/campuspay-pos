## Failure and evidence

If any phase fails, keep traffic paused and inspect the safe run summary, artifact identity and database history through an authorized read-only path. No migration runs after an earlier backup/download/restore/gate failure. If a later migration fails, its own transaction rolls back; earlier committed migrations remain. The next run deliberately refuses a partial history: fix-forward recovery requires a separately reviewed exact plan. Never serve the old app against partial/new schema, automatically retry all migrations, restore over production or unpause as cleanup. Production restore is a separate destructive action requiring explicit review.

The tool emits only fixed error codes, migration version identifiers and non-secret evidence; it never prints database rows, SQL errors, HTTP bodies, URL/password values or backup metadata. The original backup authentication and atomic-file protections remain. `release-passed-<run>-<deployment>` and `preflight-passed-<run>` artifacts contain only non-secret receipts. The backup artifact remains on failed later phases; ephemeral encrypted copies and the isolated restore database are removed. Check expiry and preserve the separately approved recovery retention plan before deleting a run.
