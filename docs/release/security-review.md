# Manual release security review

Scope: tooling PR #43 only; fixed application candidate `4e55ece88cb0afcc3e85c8f0436f8d346f5c40a1`. No live release, credentials, settings or backup uploads were used to conduct this review. PR #42 remains unchanged. The setup checklist is [github-actions-setup.md](github-actions-setup.md).

| Boundary | Implementation and verification |
| --- | --- |
| Untrusted workflow/ref | `workflow_dispatch` only; main branch and exact workflow path/SHA; no reruns. Both tooling CI workflows must have passed the current main SHA. Environment branch policy must contain only branch `main`; tags, wildcards, forks and alternate workflow refs are refused. `checkInvocation` and environment refusal tests exercise these cases. |
| Application source | Candidate checkout is a literal SHA; its tree and all 37 migration hashes are checked. Candidate code is not installed or executed: only SQL is used. The two recorded application CI runs must still report success for the fixed candidate. |
| Human approval | A job without environment secrets checks all three environments first. Each requires the exact owner reviewer and no administrator bypass. Secret-using operations recheck current protection and the recorded approval for this first run attempt. An approval setting alone does not count as action-time approval. |
| Secret scope | Owner URL and Vercel credential exist only in protected preflight/production environments; backup key only in production. They are passed only to relevant steps. No credential-bearing argv, `set -x`, repository credential persistence, untrusted input interpolation into shell code, HTTP error bodies or database rows are logged. Dependencies install with lifecycle scripts disabled before secret steps. |
| Least-privilege CI token | Contents/actions/deployments read only. Environment/branch-policy/review API reads require Actions read according to GitHub docs; no broader personal token fallback is implemented. Actions and restore-service image are immutable pins. |
| Backup destination | An exact policy value plus a separate protected action-time approval is required before capture/upload. Only the encrypted `.cpbackup` file is uploaded. Actual artifact run, SHA, digest, size and retention are checked; downloaded ciphertext must match the original digest. Key retention is separate. Private repository readers can download ciphertext and maintainers can delete it; this destination remains a user decision. |
| Restore before mutation | The supported restore tool authenticates the envelope before creating anything, accepts only localhost, creates its own random database, restores complete objects/ACLs and compares every table digest. The production owner connection for migration opens only after that downloaded-copy restore succeeds. Native tests cover wrong-key/tampered backups and restore cleanup. |
| Database target/authority | Direct pinned hostname, database, owner role and verified TLS are required. URL overrides/poolers/other users are refused. Both runtime roles must have safe flags, expected membership and API privileges, with no public/private table or schema/database creation authority. Native tests inject grant, role and membership drift. |
| Migration boundary | Exact 32-version baseline and five pending files only. All final gates run under advisory lock 84632291 before first DDL; backup age/live contents and quiescence are rechecked. Per-file transactions/history remain. Completion re-reads committed history under the lock. Native tests verify lock ownership, exact five, unchanged wallet ledger and transaction rollback. |
| Failed/uncertain results | Failed backup/download/restore/approval/target checks stop before migration. Failed SQL rolls back that file while earlier commits remain. Duplicate, partial, unknown or extra history is refused on subsequent attempts. No rollback, automatic retry, restore-over-production or automatic unpause is implemented. |
| App/schema coordination | Authorized read-only Vercel verification requires exact project/team, paused state, automatic domain assignment disabled, READY production build of the qualified SHA and Vercel pause responses at both origins. Each alias must currently belong to this project. After operator promotion, each current alias and the project production target must point to the exact deployment recorded by the successful migration run. Tests reject same-commit/different-build evidence and historical aliases. |

The final review tightened three checks: deployment-bound success receipts, current alias inspection instead of historical alias lists, and re-reading committed migration history instead of trusting the runner's intended result. Actionlint validates workflow structure and action input names; policy and native PostgreSQL tests provide behavior evidence.

Remaining trust/prerequisites are explicit: GitHub control-plane and reviewed main integrity; actual private-repository approval-plan support; explicit storage access/retention/deletion consent; independent secure key retention; authorized Vercel read/staging/promotion; operator confirmation that all alternate/local writers and recovery work are stopped; confirmation that the deployment's runtime endpoint still maps to the approved Neon branch. The workflow cannot establish physical hardware acceptance or privately inspect the app's effective connection secret. It refuses missing machine-verifiable evidence and does not replace the remaining operator checks with a synthetic green test.

Current read-only observation: the existing `Preview` and `Production` environments have no required reviewers and permit administrator bypass. Their existence does not prove required-reviewer support. The account plan was not exposed; no settings mutation was used to probe feature availability. The proposed environments must be verified before secrets are entered. Earlier Vercel 403/404 access denial was not bypassed.
