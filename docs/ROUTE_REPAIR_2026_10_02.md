# Route, credential and operator-flow repair — 2 October 2026

Baseline: 7c93e40a30a0dcac489299f1cf85fc4d3fcc8a60, following the route/database audit.
This implementation must pass the full candidate and actual-main workflows; local
syntax checks are not deployment certification. Do not copy test credentials to Neon.

## Delivered contract

- Credential state distinguishes roster-only, ready, card-required, card-only and
  other incomplete accounts. Normal PIN reset/card replacement cannot issue a first
  credential. Roster-only entries link to deliberate enrollment. A Super Admin may
  repair a card-only account through fresh purpose-bound authorization and explicit
  identity verification. It inserts only the missing PIN; existing student, card,
  wallet, balances and history remain unchanged. Migration itself issues nothing.
- A malformed/non-JSON response is an unknown outcome, regardless of its HTTP
  status. Financial clients keep recovery references and do not assert that nothing
  posted. Network failures never automatically retry. Error bodies and upstream
  details are not echoed. Valid application rejections remain distinguishable.
- Stock removal stores only its opaque request reference, scoped to the operator,
  before posting. A refresh/new session can recover the original result. Both
  execution and recovery use the same transaction advisory lock. Replay requires
  the same actor and complete payload. Closing a missing request fences late
  execution. Corrupt/unavailable local storage blocks posting, not recovery evidence.
- POS displays server-recorded intent/sale lines, not cached catalog prices. A failed
  receipt read after settlement is returned as an unknown response, never rejection.
- Operational readiness shows each application/database switch and dependencies,
  distinct from authorization. This read-only page enables no gates or credentials.
- UUID route segments and date/pagination inputs are checked at the HTTP boundary.
  Output-schema/invariant failures remain server failures, not invalid user input.
- Nested enrollment, cash-history and item-refund pages retain parent navigation.
- Daily reconciliation now compares receipt headers to line allocations and lot
  unit costs/quantities to receipt lines. Numeric unit-cost rounding uses six places.
- New migrations record SHA-256 digests. Historical rows without digests stay
  explicitly unverified; today's source is not retrospectively declared applied.
  CI captures installed API/private function fingerprints from fresh PostgreSQL.
  `verify-installed-functions.mjs` compares a pinned target read-only with that
  artifact. It never edits a function to make the comparison pass.

## Rollout sequence

1. Review exact candidate and require every existing/new validation stage.
2. Preserve current function definitions, migration inventory and account-state counts.
3. Rehearse migrations 20261002040000, 20261002041000 and 20261002042000 on disposable
   PostgreSQL and check forward upgrade, permissions, rollback and concurrency.
4. Apply those exact migrations using owner-side tooling, not the application URL.
   Keep the historical migration files and financial journals unchanged.
5. Deploy the matching application; visit `/settings/readiness` as Super Admin.
6. For the known card-only account, use Security → Complete missing PIN. The actual
   student enters their new PIN privately after identity/card verification. Do not
   use ordinary reset, duplicate enrollment or raw owner SQL to invent credentials.
7. Check the original student/card/wallet IDs, successful login, and repair audit.

## Explicit outstanding audit scope

These are not closed by the core repair patch:

- Live application/environment activation, controlled financial exercises, real
  hardware acceptance, retained live backups and key custody.
- The old DEMO-RCV-000001 header/installed bootstrap body discrepancy. Detection is
  fixed here, but no original cost value is silently rewritten or bootstrap rerun.
- Order-history pagination beyond the current 50/200 limits.
- Shared persistent picking/assignment, complete product lifecycle, formal stocktake,
  store opening/cutoff and delivery-location operator controls.

Keep the production tracker open. An implemented repair is not evidence that a
live account was repaired, a feature was enabled, or a deployed browser accepted it.
